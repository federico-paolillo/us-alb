## Purpose / Big Picture

After this work, a developer can import `backend/seed-data/us-albatese-demo.tar.gz` into a new Strapi 5 database and immediately receive a coherent, published Italian U.S. Albatese demonstration site for season 2026/27. The imported content will include the three institutional pages, news, calendar entries, official documents, eight unmistakably synthetic magenta placeholder images, three sample PDFs, their Strapi media/component links, and the minimum unauthenticated read permissions used by the existing frontend CMS client.

The result is observable without a browser. Import the archive into a unique empty SQLite database, start Strapi on `127.0.0.1:65102`, and make unauthenticated requests to the six existing REST collection/singleton endpoints. Each response must contain published content and populated media with the expected relationships; every returned image and PDF URL must download successfully. The extracted archive must contain content, schema, link, and upload records but no configuration stream, administrator record, API or transfer token, user record, webhook configuration, local credential value, or environment file.

This task changes no content type, frontend architecture, dependency, runtime, or generated API contract. It uses the schemas approved in task 01 exactly as committed at `2bcd098`.

## Idempotence and Recovery

Asset input generation is deterministic: exact dimensions, pixels, semantic names, PDF text, and PDF object layout produce the same input bytes on every clean run. Strapi output is semantically reproducible but not byte-identical because it generates media hashes, document ids, timestamps, responsive variants, and tar metadata. Validate content rather than comparing the final archive hash to a hard-coded value.

The builder refuses a nonempty database or media library. To retry after a content error, stop and destroy Strapi, preserve the failing workspace, make a new unique authoring database and empty upload directory, regenerate from the manifest, and re-export. Do not delete records piecemeal in a failed database and call the result clean.

Import is destructive by design, so it runs only against a newly created task path whose database file is proven absent. A failed import is never retried in place; create a new `task-02-import-XXXXXX` directory. `--force` is safe only because the exact target is unique and empty.

Upload isolation is the most important recovery rule. The pre-task `backend/public/uploads` directory is moved, never copied over or deleted. On any error, first stop Strapi, move the task-created upload directory aside, and restore the preserved original path. If restoration cannot be proven, stop and report `BLOCKED` rather than cleaning the workspace. Do not use a broad `rm -rf`; only remove resolved paths with the exact task prefix after restoration and validation.

The final archive is promoted only after candidate validation. If a pre-existing final archive is found, do not overwrite it silently.
